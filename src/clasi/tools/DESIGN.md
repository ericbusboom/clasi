# clasi.tools

**Owner:** clasi maintainers · **Last reviewed:** 2026-08-21 (sprint 033) · **Status:** stable

---

## 1. Purpose

`clasi.tools` holds every `@server.tool()`-decorated MCP tool function CLASI exposes to agents: artifact lifecycle operations (sprints, tickets, issues), SE process access (skills, agents, instructions, status), and design-doc-set validation. It is the subsystem boundary between "business logic that manipulates project artifacts" (which mostly lives in `clasi.sprint`/`clasi.ticket`/`clasi.issue`/`clasi.project`, all loose top-level modules) and "the MCP-callable surface an agent actually invokes" — this directory is thin wrappers plus orchestration, not where the artifact classes' own logic lives.

## 2. Orientation

Four modules — three tool modules split for file-size isolation rather than for a deep conceptual boundary (per `design_tools.py`'s own docstring), plus a new shared base:

- `_common.py` (new, sprint 030) — `@clasi_tool`, the decorator every `@server.tool()` function in this package now also carries, and `resolve_artifact_path` (relocated here from `artifact_tools.py`; already root-anchored since sprint 029, unchanged in behavior by the move). `@clasi_tool` strips the `"NONE"` sentinel per-call in owned code (replacing the `mcp_server.py` monkey-patch over `_tool_manager.call_tool` — see root `DESIGN.md`'s sprint-030 entry), converts a domain exception (`ValueError`, `FileNotFoundError`, and the artifact model's own exception types) into one `{"ok": false, "error": {...}}` result shape instead of letting some tools raise and others return an ad hoc `{"error": ...}` dict, and appends the per-call `mcp-calls.jsonl` trace (duration, args, ok/fail) that used to be written by the same monkey-patch. Composed as `@server.tool()` over `@clasi_tool` over the tool function itself — `clasi_tool` runs first on every call (strip sentinel, dispatch, catch, trace), `server.tool()` still sees the original function's signature for MCP schema generation. Deliberately does *not* own `gitutil.run_git` — see root `DESIGN.md`'s sprint-030 entry on `gitutil.py` for why. **As of sprint 033**: the `mcp` 1.x→2.x migration this module was built to survive (per its own module docstring) landed in `mcp_server.py`, and `_common.py` required zero changes — no import of `mcp`, `mcp.server.fastmcp`, or any FastMCP/MCPServer type anywhere in this file, confirmed by grep before and after the migration. This is the design working as intended, not a coincidence: `clasi_tool` is a plain `functools.wraps` closure over the wrapped function's own `*args`/`**kwargs`, with no dependency on how the caller (`@server.tool()`) is implemented on either side of the 1.x/2.x boundary.
- `artifact_tools.py` — the largest module (roughly 100KB per its sibling's docstring): create/query/update tools for sprints, tickets, issues, and briefs — the bulk of CLASI's MCP surface. Also owns the design-overlay seed path: `seed_sprint_design_overlay` accepts either a bare canonical-doc basename (resolved relative to `docs/design/`, the system-doc/legacy form) or a co-located canonical source path such as `src/firm/app/DESIGN.md` (resolved relative to `project.root`, no `../../` escape — sprint 025's `_resolve_overlay_doc_path`); a co-located path is no longer required to be a bare filename hardcoded against `docs/design/`. A sibling helper, `_derive_overlay_slug`, derives a unique per-doc overlay slug from each co-located path's components relative to its enclosing `project.sources` root (e.g. `src/firm/app/DESIGN.md` -> `firm-app-DESIGN.md`), so multiple subsystems' same-named `DESIGN.md` docs seeded in one call land as distinct overlay files instead of colliding. As of sprint 026, `_close_sprint_full`'s frontmatter-fence-error and sprint-id-mismatch precondition branches also call `db.write_recovery_state(...)` with the offending `sprint.md` path — the same pattern its ticket-not-done branch already used, now applied consistently across all three precondition-failure branches so every recovery instruction `close_sprint` hands out is one role-guard will actually honor. As of sprint 028, `get_sprint_phase` (which calls `StateDB.get_sprint_state`, not `detail_sprint`/`get_sprint_status` — neither of those reads DB phase state) additionally returns the sprint's `phase_transitions` history (from `state_db_class.py`'s new table, see the root `DESIGN.md`'s sprint-028 entry) as a timestamped `from_phase`/`to_phase`/`at` list, so per-phase wall time is readable without a direct DB query. As of sprint 029, every git subprocess this module spawns (branch detection, merge, tag push, branch delete, worktree pruning — previously inconsistent, since only the version-bump/db-guard calls passed `cwd=str(project.root)`) routes through `gitutil.run_git(args, cwd=project.root)` (see root `DESIGN.md`'s sprint-029 entry), so `close_sprint` always operates on the actual project repository regardless of the server process's own cwd; CLASI-generated commits stage and commit only the specific paths a step just wrote, via explicit pathspecs; `resolve_artifact_path` anchors a relative input path to `project.root` instead of the server process's cwd. **As of sprint 030**: `close_sprint` is now a thin wrapper delegating to `close.SprintCloser` (new top-level module, see root `DESIGN.md`) — the ~950-line `_close_sprint_full` orchestration that used to live entirely in this file has moved; this module still owns the `@server.tool()`-decorated entry point, argument handling (including the new `test_command="SKIP"` sentinel), and the envelope `@clasi_tool` applies. `update_ticket_status(path, "done")` now performs the frontmatter write and the `tickets/done/` move together (delegating to `Ticket.move_to_done()` internally rather than requiring a separate `move_ticket_to_done` call); `move_ticket_to_done` remains as a thin alias calling the same combined path, not a second independent implementation. `list_tickets` returns an error result (via `@clasi_tool`'s envelope) for an unknown `sprint_id` instead of a silent `[]`. **As of sprint 031**: `create_ticket`'s ticketing-eligibility check reads the recorded `architecture_review` gate result directly instead of comparing the sprint's phase index — a more honest check, since the gate result (not the phase string) is the real precondition — and, on a sprint's first `create_ticket` call, auto-advances the phase to `"ticketing"` via the new `StateDB.advance_to()` (see root `DESIGN.md`'s sprint-031 entry). `acquire_execution_lock` gains a `stakeholder_approval` gate check before calling `db.acquire_lock()` — no lock is granted without a recorded `passed`/`skipped` result — and, once granted, auto-advances the phase to `"executing"` via the same primitive. Neither call requires a separate `advance_sprint_phase` call by the agent; that MCP tool remains available for manual recovery only.
- `process_tools.py` — read-only tools serving packaged content: `list_agents`/`get_agent_definition`, `list_skills`/`get_skill_definition`, `list_instructions`/`get_instruction`, `list_language_instructions`/`get_language_instruction`, plus `get_version`, `get_status`, `get_use_case_coverage`, and `get_activity_guide`. As of sprint 029, `resolve_skill_body` — a pure `Load from:`-directive resolver with no dependency on `clasi.mcp_server` — moves out to a new top-level `clasi.skill_resolve` module (see root `DESIGN.md`'s sprint-029 entry); `get_skill_definition`'s three call sites import it back from there. This module's own dependency on `clasi.mcp_server` (`server`/`get_project`/`content_path`, used by its other 15+ tools) is unchanged — only `platforms/claude.py`'s indirect path through this module for one unrelated pure function is removed, which is what let an unbounded `mcp` dependency resolving to `mcp==2.0.0` crash `clasi init` (a CLI command with no business needing FastMCP at all) via this module's own top-level `from clasi.mcp_server import ...`. **As of sprint 030**: every tool function here also carries `@clasi_tool`. **As of sprint 031**: `get_skill_definition`/`get_agent_definition`'s `_get_definition` fallback (the one lookup path that did not already exclude `agents/old/` — `_list_agents_recursive`/`_find_agent_dir` already did) now excludes it too, so a lookup for a nonexistent skill or agent raises a clear "not found" error instead of silently resolving into retired content via `rglob`'s unscoped match.
- `design_tools.py` — a single tool, `validate_design`, thin-wrapping `clasi.design.validator.validate` so the MCP surface and the `clasi design validate` CLI command share one validation implementation. **As of sprint 030**: also carries `@clasi_tool`.

## 3. Constraints and Invariants

- **Tools here should not duplicate logic that belongs to an artifact class:** where `Sprint`/`Ticket`/`Issue`/`Project` already own a piece of behavior, the tool function should call it, not reimplement it — `design_tools.validate_design` is the model to follow ("no validation logic is duplicated between the two entry points", per its own docstring).
- **`design_tools.py` was kept separate from `artifact_tools.py` purely for file-size isolation, not a conceptual split:** don't read more architectural intent into that separation than exists; a future refactor could reasonably move design tools into `artifact_tools.py` or vice versa without changing behavior.
- **Every tool function is the literal contract agents depend on:** its docstring is what an agent sees when deciding how to call it (surfaced via MCP tool descriptions) — treat docstring changes here with the same care as a public API change, since it changes what calling agents believe about the tool's behavior.
- **A precondition-failure branch that names a recovery instruction must also write the recovery state that makes it actionable:** `close_sprint`'s three failure branches (frontmatter fence, id mismatch, ticket-not-done) all tell the caller to edit a specific file and retry; as of sprint 026 all three also call `db.write_recovery_state(...)` for that file, not just the one that historically did. A new precondition-failure branch that skips this call reintroduces the exact dead end sprint 026 fixed.
- **A tooling-generated commit must stage exactly the files that tooling step wrote, never a blanket `git add -A`:** as of sprint 027, `_close_sprint_full`'s version-bump step (Step 5) stages only the version file `detect_version_file`/`update_version_file` just modified — and stages/commits nothing if no version file was detected — instead of the `git add -A` it previously used, which had swept an unrelated pre-existing untracked file into a "chore: bump version" commit at sprint 026's own close. This brings Step 5 in line with the explicit-staging pattern Step 5b (three steps later, the `.clasi.db` follow-up commit) already used correctly; any future tooling-generated commit in this function should stage explicitly by the same rule, not reach for `-A`. **As of sprint 030**, this rule's home moved with the code: `close.SprintCloser`'s version-bump step, not `_close_sprint_full` (deleted).
- **Every tool function returns the uniform `{"ok": bool, ...}` envelope; none raises past `@clasi_tool` and none hand-rolls its own error shape (sprint 030):** before this sprint, three incompatible contracts coexisted (raise, return `{"error": ...}`, `close_sprint`'s own three-field shape) and a caller could not learn one rule for "did it work." A new tool function that raises a bare exception instead of letting `@clasi_tool` convert it, or that returns its own ad hoc error dict instead of the envelope, reintroduces exactly that inconsistency.
- **`"NONE"`-sentinel handling lives in code this package owns, never in a monkey-patch over a library internal (sprint 030):** `@clasi_tool` strips the sentinel per-call; nothing here reaches into `mcp`'s private `_tool_manager` or `JSONRPCMessage` attributes. This is what lets the mitigation survive an `mcp` 1.x→2.x upgrade, which deletes the internals the old monkey-patch depended on.

## 4. Design

`artifact_tools.py`, `process_tools.py`, and `design_tools.py` import `server` and `get_project`/`content_path` from `clasi.mcp_server` (the loose top-level module that owns the actual MCP server instance and stdio transport) and register tools onto that shared `server` object via the `@server.tool()` decorator at import time. None of the three constructs its own MCP server. **As of sprint 030**: every one of those `@server.tool()` functions is also wrapped in `_common.clasi_tool`, applied as the inner decorator (`@server.tool()` above `@clasi_tool` above the function) so FastMCP's schema introspection sees the original function signature while every actual call is intercepted by `clasi_tool` first.

**As of sprint 029**: a pure helper with no MCP-server dependency
(`resolve_skill_body`, previously living in `process_tools.py`) has been
extracted to a new top-level `clasi.skill_resolve` leaf module so that a
non-MCP consumer (`platforms/claude.py`'s install path) can use it
without transitively importing FastMCP. This is a narrow exception to
this section's own rule, not a reversal of it: `process_tools.py` itself
still imports `server`/`get_project`/`content_path` from `clasi.mcp_server`
unconditionally, exactly as every other tool in this package does — only
one pure, MCP-independent helper function moved out, because its second
real consumer (the CLI install path) has no business importing an MCP
server at all. Every `@server.tool()`-decorated function stays where it
was.

## 5. Interfaces

### Exposes
- Every MCP tool listed above, registered on import against `clasi.mcp_server.server` — this is CLASI's entire agent-facing tool surface, aside from a small number of tools that may be registered directly in `mcp_server.py` itself.
- **`_common.clasi_tool`** (new, sprint 030) — the decorator every tool function in this package carries; not itself an MCP tool, but the shared contract layer between all of them.
- **`_common.resolve_artifact_path`** (relocated here, sprint 030) — root-anchored path resolution for any tool taking a path argument.

### Consumes
- **`clasi.mcp_server`** for the `server` singleton and `get_project`/`content_path` helpers.
- **`clasi.sprint.Sprint`, `clasi.ticket.Ticket`, `clasi.issue.Issue`, `clasi.project.Project`** (all loose top-level modules, `clasi-core`) for the actual artifact manipulation each tool wraps.
- **`clasi.design.validate`** (from `clasi.design`, this doc set's own subsystem) for `design_tools.validate_design`.
- **`clasi.versioning`** and **`clasi.templates`** for version-bump and artifact-template support inside `artifact_tools.py`.
- **`clasi.gitutil`** (sprint 029) for every git subprocess this package's tools spawn, always rooted at `project.root`. Consumed directly by `artifact_tools.py` and `close.py` (new, sprint 030, top-level) — not re-exported through `_common.py`, see that module's entry above.
- **`clasi.skill_resolve`** (sprint 029), consumed by `process_tools.py`'s `get_skill_definition` for the `Load from:` resolver it no longer defines locally.
- **`clasi.close.SprintCloser`** (new, sprint 030), consumed by `artifact_tools.py`'s `close_sprint` tool function, which is now a thin wrapper over it.

## 6. Open Questions / Known Limitations

- `artifact_tools.py`'s size (roughly 100KB) is noted by a sibling module's own docstring as the reason `design_tools.py` was split out; whether `artifact_tools.py` itself should be further split along artifact-type lines (sprint tools / ticket tools / issue tools) is an open question this bootstrap run does not resolve. **As of sprint 030**: the close-orchestration extraction (`close.py`) is the first cut of that split, done ahead of the review's originally-planned "Phase 4, after 1-4 land" schedule because the resumability fix required the same decomposition anyway (see sprint 030's `sprint.md` Design Rationale). The sprint/ticket/issue-tool split remains unresolved.
- The raw-RPC diagnostic tap in `mcp_server.py` (`JSONRPCMessage.model_validate_json`, monkey-patched for a closed investigation) is unchanged by sprint 030's envelope work — it is permanent debug scaffolding flagged for a future cleanup pass, not part of the `"NONE"`-sentinel/call-logging mechanism `@clasi_tool` replaces. **As of sprint 033**: confirmed to still resolve under `mcp` 2.x (`mcp.types.JSONRPCMessage` mirrors the standalone `mcp_types.JSONRPCMessage`, a pydantic `RootModel` that still exposes `model_validate_json`) — this sprint's migration does not close this open question, it only verifies the tap did not silently break. The future cleanup pass is still open.
