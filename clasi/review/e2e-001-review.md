# E2E Test Review — Guessing Game CLI

Full end-to-end run of the CLASI SE process: 4 sprints driven by Claude Code
(print mode) inside a Docker container, building a stdlib Python guessing game
CLI from spec.

**Result: all 4 sprints completed, 37 tests passing, game functional.**

---

## What Went Well

### State Machine Integrity

All four sprints reached `phase: done`. All 8 architecture-review and
stakeholder-approval gates passed. Execution locks were acquired and released
cleanly per sprint. No recovery-state entries (zero failures requiring
recovery).

### Ticket Quality

Every ticket (12 total across 4 sprints) has proper YAML frontmatter (`id`,
`title`, `status: done`, `use-cases`, `depends-on`), detailed acceptance
criteria with checkboxes, and specific implementation plans with file tables.

Example structure — Sprint 001 Ticket 001:
```
id: '001'
title: Package scaffold and entry point
status: done
use-cases: [SUC-001]
depends-on: []
```
Followed by Description, Acceptance Criteria (5 items, all `[x]`),
Implementation Plan with file-create/modify tables, and Testing Plan.

### Code Quality

- Injectable I/O pattern (`input_fn`/`output_fn`) used consistently across
  every game module — makes all modules deterministically testable
- 37 pytest tests, 100% pass rate, 0.02s runtime
- Clean package structure: `guessing_game/` with `__init__.py`, `__main__.py`,
  `menu.py`, `number_game.py`, `color_game.py`, `city_game.py`
- 40 git commits with descriptive messages referencing ticket IDs
- 4 version tags (`v0.20260628.1` through `.4`)

### Logging Coverage

- 27 log files totaling 112,503 lines
- Team-lead task logs with timestamps, durations, and full transcripts
- 12 programmer sub-agent transcripts (3 per sprint × 4 sprints) with thinking
  traces
- MCP server log (821 lines) capturing every tool registration and call
- Hook log (165 lines) capturing every guard check, sub-agent start/stop, and
  task lifecycle transition

### Process Fidelity

The team-lead correctly delegated to sprint-planner for planning and
programmer for execution. The MCP guard correctly blocked the team-lead from
creating artifacts directly (line 2 of hooks.log: `blk-mcp` for
`create_sprint`). Sub-agents serialized in dependency order.

## What Needs Improvement

### 1. Sprint-Planner is Excessively Heavy for Simple Projects

Sprint-planner agents produce 3,500–4,000 word planning documents with Mermaid
architecture diagrams for sprints that implement 40-line Python modules. For
Sprint 003 (Color Game), the sprint-planner ran for ~4 minutes producing a
sprint.md, architecture-update.md, and usecases.md that are nearly identical
to Sprint 002's documents except for the secret value changing from `7` to
`"blue"`.

**Recommendation:** Add a project-complexity heuristic. For projects under a
threshold (e.g., <5 files, <3 modules, stdlib-only), use a lightweight
planning mode that skips architecture diagrams and caps plan documents at
~500 words.

### 2. Serial Programmer Dispatch Wastes Time

All 12 programmer tickets ran serially, but many are independent. For example,
Sprint 002 tickets 002 (wire into menu) and 003 (unit tests) have no data
dependency on each other — both depend only on ticket 001 (game module).
Similarly, across sprints, the color game and city game could have been
implemented in parallel.

Current dispatch times: 46–127 seconds per programmer (mean: 74s). Parallel
dispatch of independent tickets would reduce sprint execution time by ~40%.

**Recommendation:** When `depends-on` is empty or satisfied, allow parallel
dispatch of up to 3 programmer agents (matching the sprint-planner→ticket
fan-out pattern that already exists).

### 3. Version Bump Noise

There are 11 "chore: bump version" commits in the 40-commit history — one per
ticket plus one at close. This clutters git history and provides no value for a
project with no published releases.

**Recommendation:** Bump version once per sprint at close, not per ticket.
Consider a `--no-bump` flag for tickets that don't introduce user-visible
changes.

### 4. Close Reports are Inconsistent

Sprint 001's close report (generated by `close_sprint` MCP tool) is
comprehensive: 91 lines with frontmatter, ticket table with commit SHAs, code
delivered table, behavior verification, design decisions, and follow-ups.

Sprints 002 and 003 hit `max-turns` during close and were manually patched.
Their close reports are 12 lines with no frontmatter, no ticket table, and no
process notes. Sprint 004's is intermediate.

**Recommendation:** 
- Increase `max-turns` for close operations (currently 30, close consumed 25+
  turns via sub-agent dispatches).
- Add a post-close validation hook that checks for required close-report
  sections (frontmatter, ticket table, verification, test results) and rejects
  incomplete reports.

### 5. No Issue Tracker Integration

The `issues: []` field appears in all sprint and ticket frontmatter. The
`clasi/issues/` directory contains only `.gitkeep`. No GitHub issues were
created despite the MCP server having `create_github_issue` and
`close_github_issue` tools registered.

**Recommendation:** Either wire issue creation into the sprint-planning flow
(one issue per ticket), or deprecate the issue fields from frontmatter if
they're not being used.

### 6. Empty Reflections Directory

`clasi/reflections/` contains only `.gitkeep`. No sprint retrospectives were
written. The SE process schema has a reflection step but it was never
triggered.

**Recommendation:** Add a post-close gate that requires a reflection document
before a sprint can be archived to `sprints/done/`. Even a 5-line summary
("what went well / what to improve") would provide valuable process feedback.

### 7. State Machine Terminology Drift

The state DB records sprints as `phase: done`, but the state machine's
canonical terminal state is `closed`. This is consistent across all four
sprints (i.e., not a one-off bug) but creates confusion. The close report
frontmatter uses `status: closed` while the DB uses `phase: done`.

**Recommendation:** Normalize: either rename the DB phase to `closed`, or
rename the close-report status to `done`. Prefer `closed` as it unambiguously
means "finished and archived."

### 8. Architecture Updates are Repetitive

Each sprint produces a 150+ line `architecture-update.md` that restates the
entire project structure with minor additions. Sprint 004's architecture
document is nearly identical to Sprint 001's except for three new game
modules.

**Recommendation:** Make architecture updates incremental — only document
what changed from the previous sprint. The full architecture document should
live at `docs/architecture/` and be updated in-place.
