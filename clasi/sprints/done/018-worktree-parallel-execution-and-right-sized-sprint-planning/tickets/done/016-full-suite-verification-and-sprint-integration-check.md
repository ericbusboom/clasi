# Full-suite verification and sprint integration check

## Description

Final ticket of the sprint — depends on every terminal ticket of both
issue branches (008, 009, 010, 011 for Issue A's execution/cleanup
surface; 012, 015 for Issue B's process/consolidation surface — ticket
013/014 are transitively covered via 015's dependency chain). This
ticket is not a rubber stamp: it runs the sprint's end-to-end
verification scenarios described in `sprint.md`'s Test Strategy and both
source issues' Verification sections, since no single prior ticket
exercises the full cross-issue integration.

1. **Full suite**: run `uv run pytest` and confirm 100% pass, zero
   skips-that-should-be-passes, zero new warnings introduced by this
   sprint's changes.

2. **Issue A end-to-end scenario** (per the issue's own Verification
   section): create a real (or realistic fixture) sprint with
   `worktree: true` and two file-disjoint tickets; drive it through
   execution; confirm two `../worktree-<sprint>-*` directories are
   created and each is torn down **immediately on its own merge** (not
   deferred to close) — assert zero worktree directories remain mid-sprint
   after the last ticket's merge. Then simulate accumulation: manually
   leave a stale `ticket/*` worktree, attempt to start another sprint's
   worktree work, and confirm the preflight sweep + per-creation gate
   refuse to proceed until it's resolved. Confirm a `worktree: false` (or
   flag-absent) sprint still runs the serial path with zero worktree
   directories created.

3. **Issue B end-to-end scenario**: drive a small sprint through
   `create_sprint` → `detail_sprint` → ticketing → execution → close with
   a recorded `architecture_review: skipped` gate, confirming only
   `sprint.md` + `tickets/` exist at every phase (no `usecases.md`/
   `architecture-update.md` ever appear) and the sprint reaches `done`.
   Confirm `docs/architecture/` does not reappear after this close (i.e.
   `Sprint.archive()` truly never writes there anymore).

4. **Cross-issue integration check**: confirm a sprint that uses BOTH
   `worktree: true` AND the new single-doc planning model (i.e. any
   sprint planned after this sprint 018 closes) works end-to-end without
   the two features interfering — since they touch overlapping files
   (`sprint.py`, `artifact_tools.py`) but not overlapping *runtime
   behavior*, this should be a non-event, but it must be explicitly
   exercised at least once rather than assumed from separate unit tests.

5. **Report**: summarize results (pass/fail per scenario) for the
   team-lead's sprint-close review. If any scenario fails, do NOT mark
   this ticket done — fix forward within this ticket (it is the last
   ticket in the sprint; there is no "ticket 017" to defer to) or, if the
   fix requires reopening architectural decisions, throw an exception per
   the sprint-planner's exception protocol (surface to team-lead) rather
   than shipping a known-broken integration.

## Results Summary

New integration/e2e test module:
`tests/system/test_worktree_and_planning_integration.py`.

- **Scenario 1 — full suite**: PASS. `uv run pytest` → 2440 passed,
  coverage 88.01% (floor: 84%). Zero failures, zero errors.
- **Scenario 2 — Issue A end-to-end** (real-git fixture, two
  file-disjoint tickets driven through `create_worktree` x2 →
  `create_ticket_branch` → commit → `validate_worktree` →
  `merge_ticket_branch` → immediate `cleanup_worktree(keep_branch=False)`
  per merge): PASS. Confirmed both worktree directories exist
  simultaneously mid-sprint, each is torn down immediately on its own
  merge (ticket 002's worktree still exists after ticket 001's cleanup),
  and zero worktree directories remain after the last ticket's merge.
  Accumulation-blocking confirmed directly against `reconcile_worktrees`:
  a stale `in_progress`-audit ticket worktree comes back in `escalated`
  (never auto-cleaned) across repeated calls, and a live worktree with no
  audit entry at all comes back in `rogue` — both are the primitives the
  controller's per-creation gate consults to decide whether to block, per
  the ticket's guidance that the gate itself is controller prose. The
  serial path (`worktree` flag absent) was confirmed to create zero
  worktree directories when driven through an ordinary
  branch-and-merge ticket lifecycle.
- **Scenario 3 — Issue B end-to-end**: PASS. Drove
  `create_sprint` → `detail_sprint` → sprint.md content fill-in →
  `record_gate_result(..., "architecture_review", "skipped")` → phase
  advances → ticketing → execution → `_close_sprint_legacy` archive.
  Confirmed only `sprint.md` + `tickets/` (+ `tickets/done/`) exist at
  every phase, `usecases.md`/`architecture-update.md` never appear, and
  `docs/architecture/` is absent both before and after close.
- **Scenario 4 — cross-issue**: PASS. A single sprint created via the
  single-doc model, with `worktree: true` set on its `sprint.md`
  frontmatter, was driven through `detail_sprint` and then a full real
  worktree lifecycle (create → branch → commit → validate → merge →
  cleanup) against that same sprint. `Sprint.worktree` read back `True`
  throughout, the sprint directory remained single-doc-shaped
  (`sprint.md` + `tickets/` only) before and after the worktree
  lifecycle ran, and `docs/architecture/` never appeared — no
  interference between the two features.
- **`AmbiguousStateError` finding (ticket 004)**: CONFIRMED, not a bug.
  Directly reproduced that a fresh sprint.md-only sprint's `open` and
  `planned` states share an identical invariant set
  (`is_sprint_doc_present`), so `evaluate_state` raises
  `AmbiguousStateError` naming both `"open"` and `"planned"`. Then
  confirmed the normal `get_status()` → `StatusReporter` path never
  surfaces this error to a caller: the pre-existing
  `_last_matching_state_from_error` fallback in
  `clasi/status/reporter.py` picks the last (most-advanced) name from the
  ambiguity list and resolves the sprint's reported state to `"planned"`.
  No fix-forward was needed.

No production source files were modified — this ticket added only the
new test module and this ticket file's own status/results update.
