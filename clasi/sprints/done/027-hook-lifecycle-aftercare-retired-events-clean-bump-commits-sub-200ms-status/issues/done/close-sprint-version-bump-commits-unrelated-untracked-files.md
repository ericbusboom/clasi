# close_sprint's version-bump commit sweeps unrelated untracked files into the release commit

## Description

Observed at sprint 026 close (2026-08-20). `config/devices.json` — an
untracked file that predated the sprint, was deliberately excluded from
every sprint commit, and belongs to no ticket — ended up committed to
master inside close_sprint's version-bump commit ("chore: bump version
to 0.20260819.1", 5b9afb7). Every agent that touched the repo during the
sprint explicitly left it alone; the close tool's bump step swept it in
anyway.

A release/bookkeeping commit generated by tooling should contain exactly
the files the tool itself changed (version file, lock file), never
whatever happened to be lying untracked in the working tree — that
silently publishes files the stakeholder never chose to commit, in a
commit whose message says nothing about them.

## Cause

The version-bump step in the close lifecycle (see `_close_sprint_full` /
the bump-and-tag helper in src/clasi/tools/artifact_tools.py, or the
dotconfig bump wrapper it shells out to) stages broadly (`git add -A` or
equivalent) instead of staging only the files the bump modified.

## Proposed fix

Stage explicitly: the bump commit adds only the version/lock files it
edited (and the close's own artifact moves if the design intends them in
that commit). If unexpected untracked/modified files are present, either
leave them untouched or fail with a clear message listing them — never
silently include them. Add a regression test: run close_sprint in a
fixture repo containing an unrelated untracked file; assert the file is
still untracked afterward and absent from every commit the close
created.
